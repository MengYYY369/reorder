# Admin UI: Internationalization (Simplified Chinese)

This document describes the implemented internationalization of the `Reorder`
Admin UI in the `Reorder` plugin.

It focuses on:
- supported languages and language selection
- the `reorder` translation namespace
- how to add a new string
- the translation contract tests
- the frozen-English rule and the stable-ID rule
- deliberate exceptions
- the English-to-Chinese glossary

## Purpose

The Admin UI ships with English and Simplified Chinese catalogs so operators
can run the dashboard in either language. The goal is:
- complete translation of plugin-provided Admin screens
- no English copy leaking into the Chinese UI, outside the documented
  exceptions below
- a reviewable, test-enforced pipeline that fails fast when a key is missing

## Supported Languages and Selection

The plugin registers two languages with the Medusa Admin dashboard:

- `en` — English (the baseline catalog)
- `zhCN` — Simplified Chinese

Each admin user selects their display language through the Medusa Admin
profile settings. The dashboard initializes i18next with the languages found
in the plugin resources (`supportedLngs: Object.keys(resources)`), so `en` and
`zhCN` appear as selectable options without extra configuration. The choice is
per user and persisted by the dashboard, not by this plugin.

## Files

| File | Role |
|------|------|
| `src/admin/i18n/json/en.json` | English baseline. Source of truth for the key set. |
| `src/admin/i18n/json/zhCN.json` | Simplified Chinese. Must have an identical key set. |
| `src/admin/i18n/index.ts` | Exports `{ en: { reorder: en }, zhCN: { reorder: zhCN } }` for the admin bundler. |
| `src/admin/i18n/translate.ts` | `translate()` helper for code outside React components, plus the `ReorderTranslate` type. |
| `src/admin/i18n/__tests__/translations.spec.ts` | Contract test. Run with `yarn test:i18n`. |

## The `reorder` Namespace

All plugin keys live under the private `reorder` namespace — never
`translation`. The dashboard's own keys live in the `translation` namespace;
registering there would let plugin keys shadow (or be shadowed by) dashboard
keys. A separate namespace makes collisions impossible.

## Adding a String

Three rules:

1. **Follow the key convention.** Keys follow `<domain>.<area>.<key>` with
   lowerCamelCase leaves, e.g. `settings.fields.defaultTrialDays`. The ten
   domain prefixes are `menuItems`, `common`, `subscriptions`, `planOffers`,
   `renewals`, `dunning`, `cancellations`, `activityLog`, `analytics`, and
   `settings`. `menuItems.<domain>` is reserved for sidebar labels.
   `common.fields` owns shared field labels; domains must not redefine them.
2. **Update both JSON files.** Add the key to `json/en.json` and
   `json/zhCN.json` in the same change. The key sets must stay identical, and
   no value may be empty.
3. **Run `yarn test:i18n`.** The contract test verifies namespace
   registration, key parity, non-empty values, and that every key literal used
   in `src/admin` resolves in the catalog.

Additional conventions:

- Every key must appear somewhere as a full string literal in `src/admin`.
  Keys built at runtime (`` t(`a.${b}`) ``) are invisible to the contract
  test. Pick keys dynamically only through a `Record` map whose values are the
  full literals (see `SECTION_LABEL_KEYS` in
  `src/admin/routes/settings/subscription-settings/page.tsx`).
- Use i18next interpolation, never string concatenation:
  `t("settings.status.persistedVersion", { version })` with
  `"Persisted version {{version}}"` in `en.json`.
- Inside React components use `useTranslation("reorder")`. Outside component
  context (route `handle`s, plain helpers) use `translate()` from
  `src/admin/i18n/translate.ts`. Type helper parameters as `ReorderTranslate`,
  never `TFunction`.

## Contract Tests

```bash
yarn test:i18n
```

Five tests enforce the pipeline:

1. **Namespace registration** — `index.ts` registers both `en` and `zhCN`,
   each exposing the `reorder` namespace.
2. **Identical key sets** — `zhCN.json` and `en.json` contain exactly the
   same keys (no missing, no extra).
3. **No empty values** — no catalog entry has a blank value.
4. **Key-literal resolution** — every string literal in `src/admin/**` that
   looks like a translation key (any of the ten domain prefixes followed by
   dot segments, single- or double-quoted) exists in `en.json`. This one net
   catches `t()` calls, key-map values, zod `message:` strings, and
   `defineRouteConfig` labels.
5. **Route-config namespaces** — every sidebar route config carrying a
   `menuItems.*` label also declares `translationNs: "reorder"`.

Run it after any change under `src/admin` — it fails fast when a key is used
but not defined.

## Frozen-English Rule

`en.json` values are byte-for-byte copies of the UI text that existed before
i18n was introduced. Do not reword English copy while migrating a file; a
wording change must go through a separate review. Translation work changes
where text comes from, not what the English says.

## Stable-ID Rule

Identifiers that drive logic are data, not copy — never pass a translated
string where an ID is compared.

The subscription settings page (`src/admin/routes/settings/subscription-settings/page.tsx`)
uses `ChangedSection` IDs (`trial` / `dunning` / `renewals` / `cancellation`)
for all logic:

- `getChangedSections` maps dirty form fields to IDs.
- the wide-impact check compares IDs.
- section labels are resolved through translation keys
  (`settings.changedSections.*`, `settings.sections.*`) at render time only.

This keeps the wide-impact warning logic language-independent: which warning
shows depends on which IDs changed, never on what any language calls them.

## Deliberate Exceptions

The following English output is intentional and documented, not gaps to fix
in passing:

- **Backend-provided labels** — labels produced by the backend, such as the
  order widget's `formatFrequencyLabel` / `frequency_label` summary text,
  discount labels, and analytics metric labels, render as received.
- **Activity-log event-type title-casing** —
  `formatEventType` in `src/admin/routes/subscriptions/activity-log/page.tsx`
  title-cases open-ended backend event-type strings (e.g. `dunning.started`
  becomes `Started`). There is no fixed vocabulary to translate.
- **`describeOfferPayload`** — cancellation retention-offer payload summary
  fragments (`3 cycles`, `resume <date>`, `10 %`) remain English. Everything
  around them is translated; the fragments are tracked for a future plan.
- **Analytics USD formatting** — USD currency values format with a hardcoded
  `"en-US"` locale in `src/admin/routes/subscriptions/analytics/page.tsx`,
  because the USD symbol placement is fixed regardless of UI language.

## Glossary

The zhCN catalog uses a fixed English-to-Chinese terminology mapping. Later
translations must keep it — use the exact strings found in
`json/zhCN.json`; do not re-translate these terms.

| English | Simplified Chinese |
|---------|--------------------|
| subscription | 订阅 |
| renewal | 续订 |
| dunning | 催收 |
| retention | 挽留 |
| recovered | 已回收 |
| unrecovered | 未回收 |
| trial | 试用 |
| plan | 计划 |
| offer | 优惠 |
| cancellation | 取消 |
| paused | 已暂停 |
| past due | 已逾期 |
| product | 商品 |
| variant | 变体 |
| customer | 客户 |
| order | 订单 |

Formatting conventions for the Chinese catalog:

- Trailing ellipses use the full-width ellipsis character (U+2026, doubled),
  not three ASCII periods.
- `ID`, `MRR`, `LTV`, and `SKU` remain Latin in the Chinese text.
- API values (option `value` strings, status identifiers) are never
  translated — only their display labels are.
