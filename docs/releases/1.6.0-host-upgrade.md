# Upgrade to reorder 1.6.0 (host handoff)

For a Medusa application already running this plugin at 1.5.0. Written against
what 1.6.0 actually ships; the host's own patch inventory and regression list
live in its `docs/plugins/2026-09-21-plugin-issues-for-source-repos.md` (§3
vendor patches, §4 regression list) and are the authoritative per-file list.

Three passages were written after 1.6.0 was published and describe what 1.6.1
adds, not what the published 1.6.0 tarball holds: *What lands in
`node_modules`*, *Read failures on the six `/store/saas/*` endpoints*, and item
5 of *After upgrading* (with their rows in the regression list). A host that
installs only the published 1.6.0 still gets the whole `.medusa/server` build
output in `node_modules`, still sees the pre-`readTenantScoped` failure answers
on those six routes, and its reconciliation still leaves a stale `SCHEDULED`
cycle chargeable; all three arrive together in 1.6.1.

## Cross-repo order — do not reorder

1. **Money units.** medusa-paypal's major/minor migration is merged in code, but
   its data migration (`medusa-saas/scripts/money-minor-to-major.sql`) has been
   dry-run only. Code and data must ship in the **same** release as the backend
   image: code that no longer scales amounts against a database that still stores
   minor units means charging 100× too much. This plugin contains no ÷100/×100
   compensation and must not gain one.
2. Publish and install `@mengyyy369/medusa-paypal@0.5.0`.
3. Upgrade the host to it and remove the vendor patches for it (§3).
4. Publish and install `@mengyyy369/reorder@1.6.0`.

Installing 1.6.0 before paypal 0.5.0 works, but native mirror rows will not
receive revised-plan events until step 2 lands — the reconcile job reports plan
changes in the meantime, so this degrades visibly rather than silently.

## What lands in `node_modules`

The tarball ships `.medusa/server/src` with every `__tests__` directory left out
— the compiled plugin the host imports, and nothing else from the build output.
Earlier versions packed all of `.medusa/server`, so an install also wrote the
compiled Playwright specs, `playwright.config.js`, the compiled `scripts/` tree
and the 28 compiled `src/**/__tests__/*.spec.js` unit specs into
`node_modules/@mengyyy369/reorder`. Measured against one and the same build
output: 400 files / 929.7 kB before, 366 files / 826.7 kB with the `src`
narrowing, 338 files / 738.4 kB with `"!**/__tests__/**"` in `files` as well
(5.0 MB unpacked → 4.5 MB → 4.0 MB), and `tar -tzf` on that final tarball lists
no `__tests__` entry. The negation is written without a `./` prefix because the
prefix makes npm ignore the pattern — on one and the same tree,
`!./**/__tests__/**` packs 366 files and `!**/__tests__/**` packs 338. The
import surface did not move: the `exports` map is byte-identical to 1.5.0's, and
every target under it still lands inside `.medusa/server/src` — `./workflows`,
`./modules/*`, `./.medusa/server/src/modules/*`, `./admin`, the `./*` catch-all
(`@mengyyy369/reorder/jobs/manual-renewal-hygiene` resolves across a slash) and
`./package.json` were each resolved through Node's own resolver against the
338-file tree and each returned a file. No host configuration changes with this
upgrade.

What a host cannot import, and could not before either:
`@mengyyy369/reorder/providers/<name>`. The plugin declares no providers —
`src/providers/` holds only the Medusa template README — so that key's target
matches no packed file and `require.resolve` answers `MODULE_NOT_FOUND`. The
packaging check is `scripts/assert-package-surface.mjs` (a repo-side script, it
is not shipped in the tarball), run as `npm run verify:package` or
`corepack yarn verify:package`: it packs, extracts the tarball with the system
`tar` — retrying with GNU tar's `--force-local`, the only form under which that
tar opens a drive-letter archive path — and exits non-zero on any `exports`
target missing from the packed tree, on any target left under `.medusa/server`
outside `src` (the path class `files` no longer ships), on any pattern target
matching no packed file unless the script lists it by name in its
`EMPTY_PATTERN_ALLOWLIST` — that is where the `./providers/*` target sits, and it
is printed as exempted rather than skipped quietly — and on a packed manifest
whose `exports` leave the check with nothing to compare.

## Database

Two migrations ship in this release. Both apply through the host's normal
`yarn medusa db:migrate` run (`README.md:147-159`), and the second one removes
rows, so read both before upgrading a database that has live renewals.

### 1. Activity log — `src/modules/activity-log/migrations/Migration20260922120000.ts`

`up()` drops `subscription_log_event_type_check` and re-adds it with 26 event
types, the added value being `subscription.creation_failed`
(`Migration20260922120000.ts:10-15`; the list matches the 26-member
`ActivityLogEventType`, `src/modules/activity-log/types/index.ts:8-35`), then
drops NOT NULL from `subscription_log.subscription_id` and
`.subscription_reference` (`:19-24`), which is what lets a creation failure be
recorded before any subscription row exists (both columns are already nullable on
the model, `src/modules/activity-log/models/subscription-log.ts:12,17`).

`down()` is destructive by design, and its statement order is the load-bearing
part (`Migration20260922120000.ts:27-46`): drop the constraint (`:28-30`), **then
delete every `subscription.creation_failed` row** (`:35-37`), then re-add the
constraint with the 25-value pre-1.6.0 list (`:38-40`), then restore NOT NULL on
the two display columns (`:41-46`). The delete has to precede the
`ADD CONSTRAINT`, because `ADD CONSTRAINT … CHECK` validates the rows already in
the table: run the other way round it aborts the rollback on any database holding
one of those rows. That is why this file was corrected in place rather than
superseded: `up()` is unchanged, so a host that already ran it has nothing to
re-apply. Rolling back still means losing those rows.

### 2. Renewal — `src/modules/renewal/migrations/Migration20260924120000.ts`

`up()` normalizes and only then constrains
(`Migration20260924120000.ts:21-87`):

- **It soft-deletes duplicate upcoming cycles.** For each subscription, every
  live (`deleted_at is null`) `renewal_cycle` row in status `scheduled` beyond the
  first one is stamped `deleted_at = now()`, `updated_at = now()` and
  `last_error = 'normalized: duplicate upcoming cycle removed by the 1.6.0
  uniqueness migration'` (`:55-82`, the marker text at `:78`). The row kept is the
  one whose `scheduled_for` already equals `subscription.next_renewal_at`,
  falling back to the most recent one and, among rows sharing that date, to the
  lowest cycle id: the ranking is entitlement match (`prefer_entitlement`,
  `:62`), then `rc."scheduled_for" desc`, then `rc."id"` ascending
  (`:65-74`, the ordering keys at `:69`). Duplicates are soft-deleted
  rather than flipped to `failed`, because the scheduler's due set selects
  `status in [scheduled, failed]`
  (`src/modules/renewal/utils/scheduler-query.ts:64`) and a `failed` row would go
  straight back into the charge queue. What the migration removed stays
  queryable afterwards through that `last_error` marker.
- **Then the invariant becomes a constraint.** It creates the partial unique index
  `renewal_cycle_one_scheduled_per_subscription` on `renewal_cycle (subscription_id)`
  restricted to `status = 'scheduled' and deleted_at is null` (`:84-86`) — one
  upcoming renewal cycle per subscription, enforced at write time. Normalizing
  first is not cosmetic: creating that index on a drifted database fails outright,
  which would break the upgrade of any host already carrying a duplicate. The
  behavior it pins down is documented in `docs/architecture/renewals.md`
  (*The one-upcoming-cycle invariant*).

`down()` drops the index and nothing else (`:96-100`). The normalized rows stay
soft-deleted and are **not** resurrected: a second chargeable cycle back on the
scheduler's list is worse than the asymmetry, so a rollback removes the
constraint without undoing the repair.

Two host-side cautions about this file:

- The index is hand-authored on purpose. The model generator cannot express the
  extra `status` predicate, so a later `medusa plugin:db:generate` has no model
  to compare it against and may propose dropping it — that drop is a regression,
  not cleanup (`Migration20260924120000.ts:11-19`).
- Plugin module migrators run in alphabetical module order, so this migration can
  run on a fresh database before the `subscription` table exists. Its
  entitlement-date lookup is therefore guarded by `to_regclass('"subscription"')`
  and degrades to newest-first ordering when the table is absent (`:35-40,60-63`);
  the quoted bare name — not `to_regclass('public.subscription')` — is what makes
  the guard resolve through the host's `search_path` exactly like the statement
  beside it does (`:41-53`).

No migration changes the shape of `subscription` or `plan_offer`: the new offer
rules live in the existing `rules` jsonb column, and native mirror rows use the
existing `reference` column (`model.text().unique()`,
`src/modules/subscription/models/subscription.ts:10`). The renewal migration
reads `subscription.next_renewal_at` (`Migration20260924120000.ts:60-62`) and
writes no `subscription` column.

## HTTP status changes on the three workflow-backed Store endpoints

`/store/saas/renew`, `/store/saas/auto-renew` and `/store/saas/redeem` changed
**which status they answer with** for a failure that is not one of this plugin's
own customer refusals. This is a contract change at release level, not an
internal cleanup: a bridge screen that today branches on `400` to mean "that
renewal is already in flight" or "there is no such subscription" stops matching
on this version, because both now answer with the status the error was thrown
as. Check that code before consuming 1.6.0.

What did **not** change: a declared refusal still answers **400 with its own
text**. That is the status these endpoints have always used for a refusal the
SaaS shows to the end customer, and the wording is pinned because the refusal is
declared verbatim. Each workflow owns its own list; no route decides on its own
what may be quoted:

| endpoint | declared refusals — 400, own wording |
| --- | --- |
| `POST /store/saas/renew` | the three `RENEW_CUSTOMER_REFUSALS` entries: mirror row, not in `manual` mode, not `active` (`src/workflows/create-manual-renewal.ts:46-62`) |
| `POST /store/saas/auto-renew` | the two `AUTO_RENEW_CUSTOMER_REFUSALS` entries: mirror row, overdue row (`src/workflows/set-subscription-auto-renew.ts:51-62`) |
| `POST /store/saas/redeem` | the nine `REDEEM_CUSTOMER_REFUSALS` entries, all raised by `resolve-redemption-code` (`src/workflows/redeem-redemption-code.ts:61-107`) |

Everything outside those lists keeps the HTTP semantics of the `MedusaError` type
it was thrown as — `not_found` 404, `invalid_data` and `not_allowed` 400,
`conflict` 409, `duplicate_error` and `payment_authorization_error` 422 — and
only what is none of those (driver and connection faults, deserialized Postgres
errors, `database_error`, `unauthorized`/`forbidden`, `unexpected_state`,
`invalid_argument`, an unrecognized shape) collapses to a **500**. In every
non-refusal case the body carries one of the route's own fixed strings and never
the engine's message; the step name plus the serialized error go to the server
log. The rule is implemented once, in
`src/workflows/utils/store-step-failure.ts` (`classifyStepFailure`, the
`PRESERVED_TYPES` table it reads, and `logUnquotedStepFailure`), and the
per-endpoint status inventory is documented in `docs/api/saas-bridge.md`
(*Failure disclosure on the three workflow-backed endpoints*).

The specific moves a host will observe, each cited to the throw site and to the
http spec that pins it where one exists:

- `POST /store/saas/renew` — `Renewal '…' is already processing` is thrown as a
  `conflict` (`src/modules/renewal/utils/errors.ts:23-28`, raised at
  `src/workflows/steps/create-manual-renewal.ts:188`) and answers **409**, where
  1.5.0 collapsed every workflow failure into a 400 that echoed the step's
  message (`v1.5.0` `src/api/store/saas/renew/route.ts:95-98`). It is
  retryable — that is what the status now says (test at
  `integration-tests/http/saas-bridge.spec.ts:744`, status asserted at `:770`).
  A 409's body text is core's own retry sentence rather than this plugin's, so
  branch on the status and not on the wording.
- `POST /store/saas/renew` — a subscription that vanishes between the handler's
  existence check and the step's own read answers **404** with the route's
  `subscription not found` (`src/workflows/steps/create-manual-renewal.ts:118-120`;
  test at `integration-tests/http/saas-bridge.spec.ts:865`, status asserted at
  `:903`), where 1.5.0 answered a 400 quoting the subscription id.
- `POST /store/saas/redeem` — an undeclared `not_found`, such as a batch whose
  variant row is gone (`src/modules/redemption/utils/errors.ts:12-13`, raised at
  `src/workflows/steps/redeem-redemption-code.ts:140`), answers **404** with the
  route's `redemption target not found`
  (`src/api/store/saas/redeem/route.ts:38-42`), while a code the store does not
  know stays **400** because that refusal is declared
  (`src/workflows/redeem-redemption-code.ts:63-66`; test at
  `integration-tests/http/saas-bridge.spec.ts:1401`, statuses asserted at
  `:1450-1451`). The customer session route runs the same workflow and classifies
  it the same way (`src/api/store/customers/me/redemptions/route.ts:62-79`), but it
  passes `preserveQuotedStatus`, so a declared refusal keeps the type the step threw
  it as and the same invalid code stays a **404** there — what that route changed is
  only the wording of a failure it does not author.
- `POST /store/saas/auto-renew` — 1.5.0 rewrote the mode from the request
  handler, so its only answers were its own inline 400s plus the body and
  tenant-ownership checks. The toggle now runs the `set-subscription-auto-renew`
  workflow, whose write step re-reads the row before updating
  (`src/workflows/steps/set-subscription-auto-renew.ts:177-183`): a row that
  vanished in between is a **404** and a `conflict` a **409**, each carrying the
  route's fixed text (`src/api/store/saas/auto-renew/route.ts:42-46`), and a
  driver fault is a **500**. The two guard refusals keep 400 but their wording
  now names the subscription id
  (`src/workflows/set-subscription-auto-renew.ts:55,60`, pinned at
  `integration-tests/http/native-subscription-mirror.spec.ts:410`), which matters
  only to a host matching the body instead of the status.

The statuses a request never gets to a workflow for are untouched: the body
validators still answer 400 (`src/api/store/saas/auto-renew/route.ts:81-92`,
`src/api/store/saas/renew/route.ts:85-90`,
`src/api/store/saas/redeem/route.ts:84-95`) and a foreign tenant is still a 404
that does not leak existence (`assertTenantVisible`,
`src/api/store/saas/lib/tenant-ownership.ts`).

## Read failures on the six `/store/saas/*` endpoints

A second boundary, separate from the workflow classification above, covers the reads
these six routes make themselves — the tenant check's `listSubscriptions` /
`retrieveCustomer` / `listCustomers`, `carts`'s and `reconcile`'s `query.graph` reads,
and the shared helper's customer read. Each is now made through `readTenantScoped`,
which asks `classifyStoreReadFailure`
(`src/modules/subscription/utils/store-read-failure.ts`) what a failed read may say,
and that function consults nothing about the error: the answer is `not_found` with
the route's own fixed sentence, while the raw cause goes to the server log.

**Read this as the host, before you consume 1.6.0: a database outage on these
tenant-scoping reads now answers 404.** It is not an accident of the rewrite and no
500 will surface it — masking a fault as an absence is the accepted decision, risk
**R1** in §D of
`.agents/specs/2026-09-25-post-acceptance-backlog.md`, taken because a fault that
answers differently from an absence is a probeable difference and the alternative
was a 400/422 quoting a table and column to the SaaS. The log line
`[reorder] <context>: tenant-scoped read failed` is where the cause is, and it is the
only place it appears.

| Endpoint | Read fault answers | What it answered before |
| --- | --- | --- |
| `POST /store/saas/auto-renew` | **404** `subscription not found` | 500, or 400/422 naming a table and column |
| `POST /store/saas/renew` | **404** `subscription not found` | 500, or 400/422 naming a table and column |
| `POST /store/saas/redeem` | **404** `redemption target not found` | 500 / internals-quoting 400; a gone customer answered **404** with core's `Customer with id '…' was not found`, and the id stayed in the text |
| `POST /store/saas/carts` | **404** `customer not found for this tenant`; **404** `No region configured for currency '<code>'` on a region *fault* | 500 / internals-quoting 400. Genuine absence of a region keeps its **400** with that same sentence — only the fault moved to 404 |
| `POST /store/saas/ensure-customer` | **404** `customer not found for this tenant` — a status this route did not answer before, reachable only on a faulted candidate read | 500 / internals-quoting 400. "No candidate found" is unchanged and still ends in an adopted or created customer |
| `POST /store/saas/reconcile` | **404** with that branch's own sentence: `Order '<id>' not found` / `Subscription '<id>' not found` / `Customer '<id>' not found` on the id lookups, `<resource> not found for this tenant` on the tenant check and the response reads | 500 / internals-quoting 400 on any of the route's nine reads |

What the boundary does **not** reach, and where a host sees no change at all: every
admin route, the store routes under `src/api/store/customers/me/**` (their customer
id comes from `req.auth_context.actor_id`, so a masked 404 would deny a caller a
resource it owns — the reads there are classified and left on core's error path on
purpose), and any store read that answers no tenant-scoping question. A declared
workflow refusal keeps its 400 on the bridge and its own status on the
customer-scoped route, exactly as in the previous section.

## After upgrading

1. **Remove the host's vendor patches** for the three areas this release absorbs
   — the tenant-ownership routes, the store subscription list serializer, and the
   `order.placed` subscriber — except the lines §3 marks as still mirrored in
   TypeScript. Leaving a patch in place shadows the plugin fix.
2. **Seed native mirror rows**, or let the hourly `native-subscription-backfill`
   job do it. It no-ops when medusa-paypal is absent. Until it has run, the two
   checkout guards cannot see provider subscriptions that predate the plugin.
3. **Confirm a single React** in the admin bundle: `pnpm why react` in the backend
   must resolve exactly one 18.x. Two copies is a white-screen class of failure,
   not a warning.
4. **Configure the three new offer rules only where wanted.** Every default is the
   pre-1.6.0 behavior: consent never flips automatically, a repeat purchase extends
   the existing row, and there is no stacking ceiling.
5. **Expect a retirement line in the log.** Upgrading puts the plugin in a position to
   retire a stale upcoming cycle it used to leave chargeable: when the reconciliation
   step keeps or moves one `renewal_cycle` row and finds a live `scheduled` row beside
   it, it soft-deletes that one and writes
   `[reorder] retired N stale upcoming renewal cycle(s) of subscription '<id>' (<cycle ids>) behind '<kept or moved cycle id>'`.
   The row keeps its id, its `renewal_attempt` children, its `status` and its
   `scheduled_for`; only `deleted_at` is stamped, so it leaves the Admin renewals queue
   and `GET /admin/renewals/:id` answers `404 not_found` for its id, while it stays
   readable through SQL. Two further lines complete the story: `withheld …` names a
   row the run selected but did not delete, because a renewal order landed on it
   between the two reads, and `restored N retired upcoming renewal cycle(s) …` means a
   workflow failure rolled the retirement back and those rows became chargeable again. **A retirement line is not
   evidence that this release's index is missing** — a `succeeded` or `failed` cycle on
   the subscription's `next_renewal_at` with one live `SCHEDULED` neighbour satisfies
   no part of the partial unique predicate and retires on a healthy database. A
   subscription holding **two live `SCHEDULED` cycles may indicate** the index was
   dropped, since that pair is exactly what
   `renewal_cycle_one_scheduled_per_subscription` refuses; check with
   `select subscription_id, count(*) from renewal_cycle where status = 'scheduled' and
   deleted_at is null group by subscription_id having count(*) > 1`, which returns
   nothing while the constraint stands.

## Regression list additions for this release

Beyond the host's §4 list, these are the behaviors 1.6.0 changes:

| Check | Expected |
| --- | --- |
| Checkout gate, both states | with a `NATIVE-` row `active`/`paused` for the product: the one-time purchase is refused `400` and **no order is created**; with `past_due`/`cancelled`: it completes normally |
| Repeat purchase | second purchase of the same product leaves **one** active row with `next_renewal_at` pushed out and `metadata.cycles_purchased` incremented, and **one** live `SCHEDULED` renewal cycle for it, with `scheduled_for` equal to the new `next_renewal_at` — the cycle that already existed is moved, not replaced. A second live `SCHEDULED` row is the double charge this release's index makes unwritable; a different product still gets its own row |
| Stale cycle retirement | a live `SCHEDULED` cycle the reconciliation leaves behind is soft-deleted with a `[reorder] retired …` log line naming both the row that went and the row it made room for, drops out of `GET /admin/renewals`, and keeps its `renewal_attempt` rows; the `having count(*) > 1` query above stays empty |
| Consent flip | with `consent_from_session` on and the session carrying the field, payment mode and mechanism change in the same update as the stored method; the activity log names the field |
| Forced renewal on a mirror row | admin force-renewal of a cycle belonging to a `NATIVE-` row is refused, not charged |
| Write side | `POST /store/saas/auto-renew` and the payment-method update both refuse a `NATIVE-` row, and the row's `payment_mode` is unchanged afterwards |
| Store list fields | `GET /store/customers/me/subscriptions` returns `frequency_interval`, `frequency_value`, `payment_mode`, `has_payment_method` |
| Creation failure trail | an order with no subscription row has a matching `subscription.creation_failed` log line naming the step, and re-running the subscriber does not duplicate it |
| Money, three-way | PayPal charged amount = admin order total = storefront displayed amount |
| Digital-goods checkout | a cart whose only address data is the region-seeded country stub completes, with a placeholder snapshot on the row |
| Reconcile foreign customer | `POST /store/saas/reconcile` with another tenant's `customer_id` answers `404`, not `{ subscriptions: [] }` |
| Failure status, `POST /store/saas/renew` | an already-processing renewal answers **409** and its body carries no cycle id; a subscription that vanished after this handler's existence check answers **404** with `subscription not found`; the three declared refusals still answer **400** in their own words |
| Failure status, `POST /store/saas/redeem` | an unknown code still answers **400** in its own words; a batch whose variant row is gone answers **404** with `redemption target not found`; no body ever carries the engine's message or a driver's `code`/`table`/`detail` |
| Failure status, `POST /store/saas/auto-renew` | the mirror and overdue guards answer **400** naming the subscription id; any other failure of the write step carries the route's own fixed text at the preserved status (**404**/**409**) or a **500** |
| Read fault, any of the six `/store/saas/*` endpoints | the route's own fixed sentence at **404**, and no body anywhere on those routes carrying a table name, a column name or core's `Customer with id '…' was not found`; the cause is in the server log line `[reorder] … tenant-scoped read failed`. A region that is genuinely unconfigured is still **400** |

## Known gaps

- `paypal.subscription.revised` is not consumed yet (awaits paypal 0.5.0); the
  reconcile job is the interim detection for plan changes.
- A native row's `next_renewal_at` can be null when PayPal's `activated` path had
  no billing date. Nothing infers a date; Admin shows it as unresolved.
- The activity log reuses `subscription.created` for an extended row,
  distinguished by `metadata.trigger_type: "order_placed_extend"`; a dedicated
  `subscription.extended` event type would need its own CHECK-constraint migration
  and was left out of this release.
