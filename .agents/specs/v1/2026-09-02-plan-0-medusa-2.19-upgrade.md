# Plan 0: Medusa 2.19 Upgrade

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move every `@medusajs/*` dependency from `2.13.6` to `2.19.0` and `@medusajs/ui` from `4.0.25` to `4.2.1`, with a green build and green integration tests.

**Architecture:** Version numbers in `package.json` only — `devDependencies` and `peerDependencies` must stay in lockstep because the plugin declares the same packages in both. No source changes are planned. The user has already run this plugin successfully on 2.19, so this plan treats source incompatibility as unexpected and gives it an explicit escape hatch (Task 4) rather than assuming it away.

**Tech Stack:** Yarn 4.4.1 (`nodeLinker: node-modules`), `medusa plugin:build`, Jest 29 + `@swc/jest`.

## Global Constraints

- All code, comments, docs, and commit messages in English, regardless of chat language (`.agents/AGENTS.md`).
- Commit messages use Conventional Commits: `type(scope): description`.
- Present the commit message to the user and wait for explicit approval before committing or pushing.
- Do not add new external dependencies to `package.json` without asking the user first. Version bumps of existing entries are in scope for this plan; brand-new packages are not.
- Never modify generated files by hand (`.medusa/` is build output).
- Do not refactor unrelated files.

## Facts established before writing this plan

Verified against the npm registry and unpkg on 2026-09-02:

- `2.19.0` is the only stable `2.19.x` release and is the `latest` dist-tag for `@medusajs/medusa`, `framework`, `admin-sdk`, `cli`, `icons`, and `test-utils`. All six publish `2.19.0` in lockstep. Anything matching `2.19.1-*` is a preview/snapshot and must not be used.
- `@medusajs/ui` has no `2.x` line — it versions independently. Current is `4.0.25`; `latest` is `4.2.1`. `@medusajs/dashboard@2.19.0` depends on `@medusajs/ui@4.2.1` exactly, so pinning `4.2.1` matches what the dashboard loads and avoids two copies of the UI library.
- `@medusajs/ui@4.2.1` still exports every component this repo imports. Confirmed the full export list in `dist/cjs/index.d.ts`: `Alert`, `Button`, `Container`, `Drawer`, `DropdownMenu`, `FocusModal`, `Heading`, `IconButton`, `Input`, `Label`, `Select`, `StatusBadge`, `Switch`, `Table`, `Tabs`, `Text`, `Textarea`, `toast`, `usePrompt` — plus `export * from "./blocks/data-table"`, which re-exports `DataTable`, `useDataTable`, `createDataTableColumnHelper`, `createDataTableFilterHelper`, and the types `DataTableFilteringState`, `DataTablePaginationState`, `DataTableSortingState`, `DataTableRowSelectionState`. That is the complete set of 26 names this repo imports from `@medusajs/ui`.
- `@medusajs/icons@2.19.0` still exports all 15 icons this repo imports: `ArrowPath`, `Calendar`, `CheckCircle`, `EllipsisHorizontal`, `Pause`, `PencilSquare`, `Plus`, `PlusMini`, `ShoppingBag`, `Spinner`, `Trash`, `TriangleRightMini`, `User`, `XCircle`, `XMarkMini`.
- **zod major bump.** `@medusajs/admin-sdk@2.13.6`, `@medusajs/dashboard@2.13.6`, and `@medusajs/deps@2.13.6` all depend on `zod@3.25.76`, which is why `yarn.lock` currently resolves a single `zod@npm:3.25.76`. At `2.19.0` all three depend on `zod@4.2.0`. This repo imports `zod` in 13 files without declaring it, so it consumes whatever hoists. This is the one real risk in the upgrade and Task 2 is dedicated to it.
- `@medusajs/medusa@2.19.0` declares `engines.node: "^20.19.0 || >=22.12.0"`, narrower than this repo's `">=20"`. Task 3 covers it.
- `@medusajs/admin-bundler@2.19.0` depends on `vite@^7.3.6` and `@vitejs/plugin-react@^5.2.0`. This repo lists `vite: ^5.2.11` in `devDependencies`, but nothing imports vite — the only reference is a `/// <reference types="vite/client" />` triple-slash directive in `src/admin/vite-env.d.ts`. There is no `vite.config.*` in the repo. Task 3 covers it.
- `node_modules` is not installed in this workspace, so none of the above was verified by running a build. Every task below runs real commands.

## Task 2: Verify zod 4 compatibility across validators

**Files:**
- Verify: all 13 files importing `zod` (listed in Step 1)
- Possibly modify: `src/api/admin/*/validators.ts`, `src/api/store/**/validators.ts`

**Interfaces:**
- Consumes: the installed 2.19.0 tree from Task 1.
- Produces: confirmation that every `z.*` call site still compiles and behaves. No new symbols.

**Why this task exists:** zod 4 is a major release. The repo does not declare zod, so Task 1 silently moved it from 3.25.76 to 4.2.0 underneath 13 files.

The surveyed call surface is `z.array`, `z.boolean`, `z.enum`, `z.literal`, `z.nativeEnum`, `z.number`, `z.object`, `z.preprocess`, `z.record`, `z.string`, `z.union`, `z.unknown`, plus 15 `.refine`/`.superRefine` calls, 17 inline `{ message: ... }` error customizations, and 3 `.default()` calls. Two patterns deserve attention:

- All 4 `z.record(...)` calls already pass two arguments (`z.record(z.string(), z.unknown())`), which is the form zod 4 requires. zod 3's single-argument form is not used anywhere. This is already correct.
- `z.nativeEnum` is used 12 times. It is deprecated in favour of `z.enum` in zod 4 but still functional. Deprecation is not breakage — do not migrate it in this plan.

There are zero uses of `errorMap`, `invalid_type_error`, or `required_error`, which are the zod 4 changes most likely to bite.

- [ ] **Step 1: List the zod call sites for reference**

```bash
grep -rn "from \"zod\"" src/
```

Expected: 13 files — `src/admin/routes/subscriptions/plans-offers/components/create-plan-offer-modal.tsx:19`, `src/admin/routes/settings/subscription-settings/page.tsx:18`, `src/admin/routes/subscriptions/plans-offers/components/edit-plan-offer-drawer.tsx:19`, and 10 `validators.ts` files under `src/api/`.

- [ ] **Step 2: Typecheck the backend**

```bash
npx tsc --noEmit -p tsconfig.json
```

Expected: no errors. Note that `tsconfig.json:33` excludes `src/admin`, so this checks the 10 `validators.ts` files but **not** the 3 admin `.tsx` files. Step 3 covers those.

If zod 4 broke a signature, the error names the exact file and line. Fix it minimally in place — do not restructure the schema.

- [ ] **Step 3: Build, which compiles the admin extension too**

```bash
yarn build
```

Expected: `medusa plugin:build` completes and writes `.medusa/server`. This is what compiles the three admin `.tsx` files that import zod, so it is the only check covering them.

- [ ] **Step 4: Run the module integration tests**


Expected: pass. These exercise `src/modules/*/__tests__/` and require a reachable PostgreSQL with `DATABASE_URL` set (see `integration-tests/medusa-config.ts`). If the database is unavailable, record that this step could not run rather than reporting it as passing.

Pay particular attention to `plan-offers-routes.spec.ts`, which asserts the English label strings at lines 221, 230, 306, and 320. Those must still pass: this plan does not touch label generation.

## Task 3: Align engines and the vite devDependency

**Files:**
- Modify: `package.json:70-72` (engines), `package.json:58` (vite)

**Interfaces:**
- Consumes: the verified-green tree from Task 2.
- Produces: final `package.json`. No code symbols.

**Why this task exists:** two version declarations in `package.json` now disagree with what 2.19.0 expects. Neither blocks the build, so this is a correctness cleanup rather than a fix.

- [ ] **Step 1: Widen the Node engine floor**

`@medusajs/medusa@2.19.0` declares `engines.node: "^20.19.0 || >=22.12.0"`. This repo declares `">=20"`, which permits Node 20.0-20.18 — versions Medusa itself excludes. Replace `package.json:70-72` with:

```json
  "engines": {
    "node": "^20.19.0 || >=22.12.0"
  },
```

- [ ] **Step 2: Check whether vite is actually needed**

```bash
grep -rn "vite" --include="*.ts" --include="*.tsx" --include="*.js" src/ integration-tests/ scripts/
```

Expected: exactly one hit — `src/admin/vite-env.d.ts:1`, a `/// <reference types="vite/client" />` triple-slash directive. There is no `vite.config.*` anywhere in the repo.

- [ ] **Step 3: Bump vite to match the bundler**

`@medusajs/admin-bundler@2.19.0` depends on `vite@^7.3.6`. The repo's `vite: ^5.2.11` is only present so `vite/client` types resolve for that one directive; leaving it at 5 means two vite copies on disk and stale ambient types. Replace `package.json:58` with:

```json
    "vite": "^7.3.6",
```

- [ ] **Step 4: Reinstall and rebuild**

```bash
yarn install && yarn build
```

Expected: install succeeds, build succeeds. `vite/client` types resolve the same way in vite 7 (the directive only pulls in `ImportMeta` and asset module declarations).

If the build breaks on the vite bump specifically, revert only `package.json:58` back to `"vite": "^5.2.11"`, rerun `yarn install && yarn build` to confirm green, and note the revert in the commit body. The engines change in Step 1 is independent and stays either way.

- [ ] **Step 5: Commit**

Propose to the user and wait for approval:

```
chore(deps): align node engines and vite with Medusa 2.19
```

```bash
git add package.json yarn.lock
git commit -m "chore(deps): align node engines and vite with Medusa 2.19"
```
