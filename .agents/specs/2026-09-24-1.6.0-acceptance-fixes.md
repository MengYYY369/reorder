## TLDR & Overview

The 1.6.0 sequence landed all twelve tickets and every gate passes, but three
defects were proven by execution and none of them is covered by any assertion in
the 207-test http suite:

1. **Row stacking double-charges (#08).** A second purchase of the same product
   extends `subscription.next_renewal_at` but leaves the first purchase's
   `SCHEDULED` renewal cycle on the old date. `create-subscription-from-order`
   then unconditionally calls the ensure-next-cycle step, which matches cycles by
   exact date and therefore creates a second one. The row ends up with two future
   `SCHEDULED` cycles and the scheduler bills both — the exact RE-7 failure the
   ticket claims is structurally eliminated.
2. **The shipped activity-log migration cannot roll back (#01).**
   `Migration20260922120000.down()` re-adds the 25-value event-type CHECK
   constraint *before* deleting the `subscription.creation_failed` rows, so
   `ADD CONSTRAINT` fails against existing data. Ticket 01 mandates the opposite
   order. **[v2]** The release doc is not simply "repeating a wrong claim":
   `docs/releases/1.6.0-host-upgrade.md:30-32` is literally true about the
   delete-vs-`set not null` order — it just never mentions the `ADD CONSTRAINT`
   that aborts first, which is the sentence that has to change.
3. **The documentation ticket shipped docs that contradict shipped code (#10).**
   `docs/architecture/subscription-relationship-model.md` still opens with "None
   of the mechanism/rule fields described below exist in the code yet" and names
   a `payment_context.native_subscription_id` field that exists nowhere in
   `src/` (the code writes `customer_payment_reference`).

This spec also carries the verified medium findings the user ruled into the round
(two from #06, #08 metadata, #01 PII, #12 fail-open, two standards items).

The user has no customers and no data to protect, so the ruling is **fix the
class, not the instance**: establish the domain invariant structurally rather
than patching the one path that violated it, and no backward-compatibility
shims for the pre-fix behavior.

## Proposed Architecture & Data Model

### 1. The upcoming-cycle invariant (#08)

**Statement:** for any subscription that should have an upcoming renewal, exactly
**one** `renewal_cycle` row exists with `status = 'scheduled'` and
`deleted_at is null`, and its `scheduled_for` equals
`subscription.next_renewal_at`.

**(a) `ensureNextRenewalCycleStep` reconciles instead of duplicating.**
`src/modules/renewal/utils/upcoming-cycle.ts` gains a pure selector:

```
resolveUpcomingCycle(cycles, scheduledFor):
  | { action: "match"; cycle }      // exact-date hit → today's approval-state update
  | { action: "adopt"; cycle }      // a differently-dated SCHEDULED → reschedule it
  | { action: "defer"; cycle }      // [v2] that SCHEDULED row has an in-flight manual order
  | { action: "create" }            // no SCHEDULED row
```

`adopt` updates `scheduled_for` plus the approval-state fields on the row it
found, preserving the cycle id, its `renewal_attempt` children and
`generated_order_id` history. Compensation gains
`{ action: "adopted", previous: { id, scheduled_for } }`.

**[v2] `defer` is a required branch, not an edge case.** `create-manual-renewal`
reuses a due `SCHEDULED` row **without changing its status**
(`create-manual-renewal.ts:189-196`) and only stamps `generated_order_id`
(`:336-339`), while `scheduler-query.ts:64` selects
`status in [scheduled, failed]`. Moving such a row's date would re-arm a cycle
whose order is already sitting unpaid. Rule: if the only candidate SCHEDULED row
carries a non-null `generated_order_id` (or is `PROCESSING`), the step emits no
write and logs one warning naming the cycle id and the order id; the duplicate
is then surfaced by the index rather than silently tolerated. Pin it with a
test.

A **past-dated** `SCHEDULED` row with no order is adopted, not left behind:
`process-renewal-cycle` moves anything it is working on to `processing`, so an
untouched `SCHEDULED` is by definition free to follow the entitlement date.

**(b) A partial unique index makes drift impossible to write silently.**
New hand-authored migration in the renewal module:

```sql
-- up: normalize first, then constrain (creating the index on a drifted DB fails:
--     measured "could not create unique index … is duplicated")
update "renewal_cycle" rc set "deleted_at" = now(), "updated_at" = now(),
  "last_error" = 'normalized: duplicate upcoming cycle removed by the 1.6.0 uniqueness migration'
  where rc."status" = 'scheduled' and rc."deleted_at" is null
    and rc."id" not in (
      select keep.id from "renewal_cycle" keep
        where keep."status" = 'scheduled' and keep."deleted_at" is null
          and keep."id" = (
            select k2."id" from "renewal_cycle" k2
            where k2."subscription_id" = keep."subscription_id"
              and k2."status" = 'scheduled' and k2."deleted_at" is null
            order by (k2."scheduled_for" = <subscription.next_renewal_at>) desc,
                     k2."scheduled_for" desc
            limit 1
          )
    );
create unique index if not exists "renewal_cycle_one_scheduled_per_subscription"
  on "renewal_cycle" ("subscription_id")
  where "status" = 'scheduled' and "deleted_at" is null;
-- down: drop index only; normalized rows are not resurrected (documented)
drop index if exists "renewal_cycle_one_scheduled_per_subscription";
```

The exact keep-one CTE is an implementation detail to finalize on a scratch DB
against the real schema; the requirements are: it is **soft-delete** (a
`failed` status would keep the row visible to
`scheduler-query.ts:64` and re-arm it), it prefers the row already matching
`subscription.next_renewal_at`, and `down()` drops only the index.

**[v2] Why hand-written, precisely.** MikroORM *can* express a unique index and
its generator already emits soft-delete predicates in this repo —
`src/modules/redemption/migrations/*.ts:13,20` contain
`CREATE UNIQUE INDEX … WHERE deleted_at IS NULL`. What it cannot express is the
extra `status = 'scheduled'` predicate, so this index stays hand-authored. That
leaves a real hazard: a future `medusa plugin:db:generate` may try to drop it.
Mitigation is Phase 5: an in-migration comment naming it intentional plus a
`lessons.md` entry.

**[v2] Persistence boundary.** Per-run http databases are created fresh
(`Creating database medusa-<id>-integration-N`) so they only ever see `up()` on
an empty table; the persistent `reorder_test` and any host database can hold
drift, which is why `up()` normalizes before indexing.

### 5. Metadata merge on extend (#08)

`create-subscription-record.ts` builds a fresh `{ source, source_order_id }` +
`withStackedCycles(...)` object at `:84-89` and writes it wholesale onto the
existing row at `:217`. **[v3 — severity corrected twice during review]** This is
not customer-visible data loss on the default path: `updateSubscriptions` goes
through `@medusajs/utils/dist/dal/mikro-orm/mikro-orm-repository.js:224-231`,
which calls `manager.assign(..., { mergeObjectProperties: true })`, and
`@mikro-orm/core/entity/EntityAssigner.js:106-108` merges when **both** the stored
and incoming values are plain objects — so stored `payment_method_update_context`
and `pause_context` survive there. The merge is **path-dependent, not universal**:
the same repository's `nativeUpdateMany` (`:852-868`, reached from `upsert` /
`upsertWithReplace` at `:286/:351/:390`) overwrites the column, and a stored
non-object takes the non-merging branch too. The defect is therefore "the payload
the extend writer sends is incomplete and its correctness depends on which DAL
method the caller happened to use", and extend was also the only metadata writer
in the module that did not spread (`pause-subscription.ts:95`,
`resume-subscription.ts:50`, `update-subscription-payment-method.ts:124`,
`native-mirror-sync.ts:109` all do). The fix — merge into `target.metadata`,
newest purchase winning `source`/`source_order_id` — makes the contract local and
visible instead of relying on an internal option.

**[v3] Documentation rule for Phase 5, stated precisely:** jsonb column writes
merge on the single-entity update path **but not** on batch/upsert paths, and
writing `metadata: null` clears the column. Do not document "a writer can never
clear a metadata key" — that is false.

## Verification & Testing

- **Reddening is mandatory per fix** — an assertion that cannot fail is worse
  than an honest "manual only". Phase 6.4 performs the mutation rather than
  trusting an implementer's claim.
- **Where an assertion may live is decided by `jest.config.js`**, not by where
  the code lives: only `src/modules/*/__tests__/**/*.spec` and
  `integration-tests/http/*.spec` are executed, and module runners apply
  entity-derived schema rather than migrations. Any claim about migration output
  (the index) is an http-suite assertion.
- **`down()` proof** stays manual-but-mechanical: recreate `subscription_log`
  from the migration's own 25/26-value lists, insert one
  `subscription.creation_failed` row, replay `down()` verbatim, require zero
  errors under `ON_ERROR_STOP=1`; then replay the previously shipped order and
  require the constraint violation, which is what shows the probe is
  discriminating rather than tautological.
- **Normalization proof**: seed one subscription with two live `SCHEDULED` rows
  on a scratch database, run `up()`, require exactly one live row (the one
  matching `next_renewal_at`), the other soft-deleted with a `last_error`
  marker, and require the index to exist afterwards.
- **Gate interpretation**: a single unattended `yarn test:integration:http`
  cannot reach 35/35 on this machine (OS-killed workers, different suites per
