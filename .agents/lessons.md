# Lessons Learned

In this file, we record recurring patterns, encountered issues, and mistakes to avoid when working with the Reorder plugin.
It should be reviewed at the start of a session and updated after fixing any bug or resolving a complex issue.

## Rules for AI Agents

### Repository Language Constraint

- **Rule**: All files, code comments, documentation, specs, lessons, and commit messages added or modified in the repository on GitHub MUST be written in English. Even if the user interacts with you in another language (e.g., Polish), do not write Polish code comments, skill files, specs, or repository files.
- **Context**: The repository codebase and its meta-configuration (like AI agents instructions) must maintain a unified English language standard.

### Git Commits and Push Approval

- **Rule**: Before proposing a commit or git push to GitHub, always construct a Conventional Commits message format: `type(scope): description` and present it to the user. Wait for the user's explicit approval before proceeding with the commit and push.
- **Context**: Helps the user audit and accept individual changes, ensuring only well-formed commits with correct scopes are pushed.

### Local Dev Server URLs

- **Rule**: Whenever starting the local Medusa backend and storefront dev servers (via `local-dev` skill or scripts), always inspect the output logs for the running ports and immediately provide the clickable local URLs:
  - **Medusa Backend API**: `http://localhost:9000`
  - **Medusa Admin Dashboard**: `http://localhost:9000/app`
  - **Medusa Storefront**: `http://localhost:8000`
    directly to the user.
- **Context**: Prevents leaving the user guessing where the dev server, admin panel, and storefront are hosted when processes run in the background.

### Mandatory Confirmation for Test Data Wipe

- **Rule**: NEVER execute destructive reset or test data wipe scripts (such as `scripts/wipe-test-data.ts` or `wipe-test-data` skill) immediately upon request. Always first explicitly warn the user that 100% of operational data (orders, customers, subscriptions, renewals, dunning, logs, analytics) will be permanently deleted, and wait for their explicit confirmation before proceeding.
- **Context**: Protects against accidental data loss when the user invokes a wipe command or mentions clearing data without realizing the full scope.

### Post-Push Docs Sync

- **Rule**: Whenever you push code to GitHub (e.g. after resolving an issue or implementing a feature), ALWAYS proactively ask the user: "Czy zmiany wymagają aktualizacji dokumentacji (wewnętrznej w reorder/docs lub publicznej Mintlify w ../docs)? Jeśli tak, użyję skilla `sync-docs`."
- **Context**: This ensures both internal technical docs (`reorder/docs/`) and the public documentation repository (`../docs`) stay in sync with codebase changes without the user having to remember it.

### Reseeding & Database Reset Invalidation Checklist

- **Rule**: Whenever performing a full database reset, schema drop, or `yarn seed`:
  1. **Recreate Admin User**: Medusa v2 `seed.ts` does not create an admin user by default. Always recreate the admin account (`yarn medusa user -e admin@medusa-test.com -p supersecret`).
  2. **Sync Publishable API Key**: A fresh seed generates a new `publishable_api_key` in the database. Always check/update `NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` in the storefront's `.env.local` to match the newly generated key, and restart the storefront dev server.
  3. **Preserve Catalog Inventory**: In transactional data wipes (`wipe-test-data.ts`), never truncate `inventory_item` or catalog tables, as Medusa v2 requires inventory items and levels for cart item creation when `manage_inventory: true`.
- **Context**: Prevents 401 "Invalid email or password" admin login failures, 400 "A valid publishable key is required to proceed with the request" storefront errors, and 500 cart item creation failures.

### Activity Log Event Types Require a Migration

- **Rule**: Adding a value to `ActivityLogEventType` (or `ActivityLogActorType`) is not a types-only change. `subscription_log.event_type` is a Postgres check constraint, so every new value needs a migration in `src/modules/activity-log/migrations/` that drops and re-adds `subscription_log_event_type_check` with the full value list, plus a `down` that restores the previous list. Also add the new value to the Admin activity-log domain filter lists in `src/admin/routes/subscriptions/[id]/page.tsx` and `src/admin/routes/subscriptions/activity-log/page.tsx`, or the event will never be selectable in the timeline filters.
- **Context**: Without the migration, writing the new event type fails at runtime with a check constraint violation even though the code type-checks and builds.

### Payment Provider Isolation on Subscription Payment Method Queries

- **Rule**: When querying or listing customer payment methods for a subscription, always verify that `provider_id` exists in the subscription's `payment_context`. If `provider_id` is null or not configured, return `{ payment_provider_id: null, payment_methods: [] }` immediately. Never pass `provider_id: null` to core Medusa Payment Module listing utilities, as Medusa treats a null provider ID as querying across all account holders and providers, which leaks unrelated customer payment methods across different gateways.
- **Context**: In Store and Admin APIs, subscriptions that were created without an initialized payment provider context must not expose saved cards from other providers or gateways.

## General Lessons

* **Stale Tool-Snapshot Reads**: File contents shown in system reminders or context summaries can be stale after subagents modify the working tree. Always verify actual file state with `grep`/`git status` before acting on a reminder-injected read (hit during the i18n branch: files shown as untranslated were already migrated).
* **Subagent Silent No-Op**: A dispatched subagent can return "completed" with empty output and zero working-tree changes (provider hiccup). Check `git status` before assuming failure, and prefer resuming the same agent via SendMessage before re-dispatching from scratch (hit during Plan 5 of the i18n branch).
* **Medusa 2.19 Typecheck Surfaces**: `medusa plugin:build` on 2.19 typechecks `scripts/` and module tests too. Hand-written narrow connection types (e.g. a custom `PgConnection`) can break on `whereIn`/`where` — resolve `ContainerRegistrationKeys.PG_CONNECTION` untyped instead of annotating a narrow type.
* **Translation Key Hygiene for Backend-Event Strings**: Strings that are backend contract values (e.g. dunning event types `dunning.started`, `dunning.recovered`) must never become translation keys; the contract test denylists them so the key-literal scan cannot confuse logic strings with copy.

### Zod must be imported from the Medusa re-export in backend code

- **Zod imports**: In backend code (`src/api/`, `src/workflows/`, `src/modules/`, `src/jobs/`), import Zod as `import { z } from "@medusajs/framework/zod"`, never from `"zod"`. Admin dashboard customizations under `src/admin/` keep importing from `"zod"` directly, since the dashboard supplies it.

### Admin widget zones must not use deprecated position suffixes

- **Widget zones**: In Medusa >= 2.17.2 with Layout Composer, admin widget injection zones must specify the base zone (e.g. `order.details`), never legacy position suffixes like `.before`, `.after`, or `.side.after`. The merchant/administrator controls visual positioning via the dashboard's Editor view (Layout Composer), while plugins must never attempt to enforce or migrate layout configuration directly in database tables.

* **Publishable API Key Mismatch**: If Storefront throws `Error: A valid publishable key is required to proceed with the request`, the key in `.env.local` (`NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY`) is out of sync with the active key in the Medusa backend database (table `api_key` where `type = 'publishable'`).
* **Missing Inventory on Cart Line Items**: In Medusa v2, `addToCartWorkflow` checks inventory levels for all variants with `manage_inventory: true`. If `inventory_item` or `inventory_level` rows are missing, `POST /store/carts/:id/line-items` will fail with a 500 error.
* **Subscription MRR on First Billing Cycle**: Newly created subscriptions do not have a renewal cycle record yet (`latestRenewal` is null). Analytics daily snapshots must resolve the latest order from linked subscription orders (including the initial checkout order) rather than exclusively checking renewal cycles to avoid calculating MRR as unavailable or zero before the first renewal.
* **Yarn Version and Toolchain**: The repository pins `yarn@4.4.1` via `packageManager`, but the globally installed Yarn is `1.22`. Running `yarn install` or `yarn build` directly fails with a Corepack error and installs nothing. Use `corepack yarn <command>` (or enable Corepack once) for any Yarn invocation in this repository.
* **Migration Generators Need a Live Database**: `medusa plugin:db:generate` connects to Postgres before generating anything, so it cannot be used to refresh `.snapshot-medusa-*.json` when the local database is down. Hand-written constraint migrations are still valid, but the module snapshot stays stale until the generator is run against a live database.
* **Analytics Daily Snapshot Order Resolution**: When resolving `latestOrderId` for daily metric snapshots, always prefer `latestRenewal.generated_order_id` (representing the most recent renewal order) and fallback to `latestOrderBySubscription` (representing initial order creation) so that both renewal-generated orders and initial orders are properly captured.


* **E2E Prompt Scoping**: A Medusa Drawer remains open beneath its confirmation `alertdialog`; target the confirmation by `role="alertdialog"` and accessible name rather than a generic dialog locator to avoid strict-mode conflicts.
* **E2E Tests & Vite Dependency Cache Invalidation**: Browser E2E tests (`yarn test:e2e`) run against the local Medusa backend (`my-medusa-store`), which pre-bundles plugin admin code in `node_modules/.vite/deps`. If backend admin UI behavior is stale or diverges from the current plugin source (e.g., outdated form validation logic), rebuild and push the plugin (`yarn build && npx yalc push`), clear Vite cache (`rm -rf ../my-medusa-store/node_modules/.vite`), and restart `medusa-backend`. Ensure Playwright binaries are installed via `npx playwright install chromium`.
* **Nullable Number Inputs in React Hook Form**: When registering optional number inputs validated by Zod's `.positive().nullable()`, never use `setValueAs: (value) => value === "" ? null : Number(value)`. Untouched fields initialized with `null` in `defaultValues` pass `null` to `setValueAs` on submit; since `null === ""` is `false`, `Number(null)` evaluates to `0`, failing Zod's positive constraint with `"Number must be greater than 0"`. Always check `value === "" || value === null || value === undefined ? null : Number(value)`.
* **Integration Tests Worker Concurrency vs in-band OOM**: Running all backend HTTP integration tests with Jest's `--runInBand` in a single Node process causes cumulative heap growth (~200 MB per test suite) from repeated Medusa v2 container initializations and MikroORM/Knex metadata caches, eventually exhausting the default 4 GB V8 heap limit (`JavaScript heap out of memory`). Use `--maxWorkers=2` instead of `--runInBand` so tests run in isolated worker processes, eliminating the memory leak and cutting execution time by more than half without database or port collisions.
* **Admin List Endpoints Must Accept the Sorting Params the Dashboard Sends**: The Medusa Admin DataTable (`page-view.tsx`) always sends `order` (default `created_at`) and `direction` (`asc`/`desc`) query params to list endpoints. A list validator built only with `createFindParams().extend({...})` rejects `direction` with a 400 ("Unrecognized fields"), which renders the admin list permanently empty ("No results") even though data exists. When adding a new admin list route, mirror the sibling pattern (e.g. `cancellations/validators.ts`): declare `direction: z.enum(["asc","desc"]).optional()` in the validator and honor it in the route's service `order` option.
* **Plugin Admin Icons Must Exist in the Host's `@medusajs/icons` Version**: Icons referenced in `defineRouteConfig` / route files (e.g. `Ticket`) may not exist in the `@medusajs/icons` version installed by the consuming backend, which fails the host's admin bundle build with `"X" is not exported by "@medusajs/icons"`. Verify the icon export exists (`node -e "console.log(Object.keys(require('@medusajs/icons')).filter(n=>...))"`) before using it; `ReceiptPercent` is a safe choice for redemption/monetization menu entries.
* **Passing Selection Between Chained Admin Picker Modals**: When chaining `PlanOfferProductPickerModal` → `PlanOfferVariantPickerModal` outside the plan-offers page, the variant picker's products query is `enabled: open && Boolean(productId)` — the component silently renders its "Select a product first." empty state if `productId` is not forwarded. Keep a dedicated `selectedProductId` state (not the form's `variant_id`) and pass it as `productId` to the variant picker.
* **E2E Custom-Code Uniqueness Across Tests in One Run**: Module-level `Date.now()` fixtures in a Playwright spec file share one value across all tests in the run; a second test re-creating the same unique-keyed entity (e.g. a custom redemption code with a `LOWER(code)` unique index) fails with a server error and only a generic toast. Generate unique fixture values inside `beforeEach` (e.g. `${Date.now()}${Math.floor(Math.random()*1000)}`), and in product/variant pickers search for the seeded entity and assert its row is visible before clicking, instead of blind-clicking the first row.
* **Medusa v2 Admin Bundle Layout in Consumer Backends**: `medusa start` serves the admin from `<backend root>/public/admin` (`ADMIN_RELATIVE_OUTPUT_DIR = "./public/admin"`), but `medusa build` writes it to `.medusa/server/public/admin`. If `medusa start` fails with "Could not find index.html in the admin build directory", copy `.medusa/server/public/admin` → `public/admin` in the backend root. Also, `medusa develop` (Vite dev server) tolerates missing peer deps that the production Rollup build needs (`@medusajs/icons`, `@medusajs/js-sdk`) — a backend that runs in develop mode may still fail its production admin build until those peer deps are installed.
* **Medusa 2.20 Read-Time `pending_difference` Epsilon Zeroing**: The query layer recomputes order totals at read time (`decorateCartTotals`): `pending_difference = total − pending_return_total − transaction_total`, zeroed whenever the result is ≤ the currency epsilon (`10^-decimal_digits` — 0.01 for USD/CNY, but 1 for zero-decimal currencies like JPY/KRW). The persisted `order_summary` jsonb is always correct; the zeroing happens only on reads. Any logic that validates a charge against an order summary read therefore breaks on fresh orders priced at or below the currency epsilon — the core `createOrUpdateOrderPaymentCollectionWorkflow` throws `Amount cannot be greater than [object Object]` before the charge, and the failure bypasses dunning classification. Rule: never validate charge amounts against order summary reads on Medusa 2.x; manage renewal payment collections through the plugin-owned `resolveOrderPaymentCollection` helper (`src/workflows/utils/resolve-order-payment-collection.ts`), which reuses/updates `not_paid`/`awaiting` collections, cancels-and-replaces `authorized`/`partially_authorized` ones (never canceling captured money), and otherwise creates a new collection plus the order ↔ payment collection link.
* **Integration Test Runner Needs Explicit DB_* Env Vars**: `medusaIntegrationTestRunner` creates its per-run database through `DB_HOST` / `DB_PORT` / `DB_USERNAME` / `DB_PASSWORD` env vars (defaults: empty user/password), NOT `DATABASE_URL`. With the local test container `reorder-acceptance-pg` (`AGENTS.md` *Validation Commands* carries the pasteable start-or-create block and the `pg_isready` check that must answer `accepting connections` before you blame code for `ORM not configured`; the older name `medusa-epay-pg` names a container that does not exist on this machine, so following it is a dead end) run suites as `TEST_TYPE=integration:http DB_HOST=localhost DB_PORT=5432 DB_USERNAME=user DB_PASSWORD=<password decoded from .env's DATABASE_URL> corepack yarn jest --forceExit integration-tests/http/<spec>.spec.ts`, filling that placeholder from the `new URL()` one-liner in `AGENTS.md` and never by pasting a literal — the credential that belongs in the slot may itself read like a placeholder, which is why it must not appear in a tracked file (the URL form also discards a stray trailing `\r`, which a hand-rolled `cut`/`sed` slice can keep). `AggregateError` on every test means the container is down; `SASL: client password must be a string` means `DB_USERNAME`/`DB_PASSWORD` were not set. The test app boots the plugin from compiled `.medusa/server/` — not `dist/` — because `package.json` `exports` map every module to `./.medusa/server/src/modules/<dir>/index.js` and `@medusajs/modules-sdk/dist/loaders/utils/load-internal.js:367` resolves that specifier with `require.resolve` and derives the module's `migrationPath` from it (`:419`), so run the documented gate build command `corepack yarn build` after changing `src/` before running integration tests, or the suite exercises stale plugin code while the spec imports fresh `src/` workflow handles.
* **Workflow Engine Drops Step Names On Throw**: `engine.run(id, { throwOnError: true })` re-throws `errors[0].error` only (`workflow-engine-inmemory/dist/services/workflow-orchestrator.js`), so the failing step's `action` never reaches the caller and non-`Error` rejections degrade to `[object Object]` in logs. When a subscriber needs to report *which* step failed, run with `throwOnError: false` and read `result.errors` (each entry carries `action` plus the nested `error`), and treat `result.acknowledgement.hasFailed` as the failure signal. Serializing that array requires cycle detection plus a `errors`/`error`/`err`/`cause` walk — see `src/modules/activity-log/utils/serialize-error-chain.ts`.
* **Subscribers Never Import `src/workflows/**`**: every subscriber invokes workflows by name through the engine, so a pure helper a subscriber needs (e.g. the `subscription_log` write path) must live under `src/modules/<domain>/utils/`, not in a step file — importing a step file pulls its `createStep(...)` registration into the subscriber's module graph. Moving such a helper means updating every importer in the same change; `yarn build` catches them because `medusa plugin:build` typechecks the backend (`tsconfig` excludes `src/admin`, so admin files are NOT caught).
* **A Plugin May Guard A Core Route With A Method Middleware**: `src/api/middlewares.ts` can register `{ matcher: "/store/carts/:id/complete", methods: ["POST"], middlewares: [...] }` for a path the plugin does not own — the file loader only requires `matcher`, and `RoutesSorter` puts method-scoped middlewares in the insertion-ordered static bucket, ahead of the route for the same path (verified in a container test: the guard answered 400 and no order row was created). What you must NOT do is add `src/api/store/carts/[id]/complete/route.ts`: only one registration survives per `(matcher, method)`, so that deletes the core handler from the app. Do not reach for a `completeCartWorkflow` `validate` hook either — the core route runs that workflow without hooks, and `run()` accepts no `hooks` option. Finally: answer with `res.status(400).json(...)` rather than `throw new MedusaError(...)` when the body must carry structured `data`, because the core error handler emits only `{code, type, message}`.
* **Type Predicates Break The Negative Branch**: a guard written as `function isComplete(x?: Record<string, unknown> | null): x is Record<string, unknown>` narrows `x` to `null` in the `else` branch, so `x?.foo` reports `Property 'foo' does not exist on type 'never'` under `strictNullChecks`. Return plain `boolean` and guard with `if (x && isComplete(x))` when the fallback branch still needs to read fields off `x`.
* **Cart Region Country Lives At `region.countries.iso_2`**: a Medusa v2 region has no `country_code` column — countries are a many-relation carrying `iso_2`. `query.graph` on entity `cart` resolves `"region.countries.iso_2"`, and a region created through `regionModule.createRegions({ countries: ["de"] })` (a single object returns a single entity, not an array) is enough to make it non-empty. Carts built with a bare `cartModule.createCarts({ currency_code })` have `region_id: null`, so anything falling back to a region country must seed a region in the test.
* **Plan-Offer Rules Are Copied Key-By-Key In Five Places**: `rules` is a jsonb column, so adding a field needs no migration — but four separate mappers pick keys explicitly (no spread), and a field missing from any one of them disappears silently: `planOfferRulesSchema` (`src/api/admin/subscription-offers/validators.ts`), `normalizeRules` (`src/workflows/steps/shared-plan-offer.ts`, the WRITE path — skip it and Admin submissions never persist), `mapRules` (`src/modules/plan-offer/utils/admin-query.ts`, the READ path), and both admin forms (`zod` + `defaultValues` + detail `form.reset` + submit + JSX). Read new fields through `resolvePlanOfferRules` (`src/modules/plan-offer/utils/rules.ts`) so legacy rows without the key get the documented default in one place. None of the admin sites are typechecked by `yarn build` (`tsconfig` excludes `src/admin`); only the i18n contract test (`TEST_TYPE=i18n npx jest`) catches a mistyped `t()` key.
* **Tenant Ownership Has Two Semantics, Not One Comparison**: `/store/saas/*` needs a *visibility* rule (own stamp = visible; no stamp = visible only on a single-tenant host; foreign stamp = 404) and `ensure-customer` needs an *adoption* rule (no stamp = claimable, **independent of how many tenants are configured**). Collapsing both into one predicate silently breaks adoption on single-tenant hosts, because `isTenantVisible` returns true for an unclaimed customer there and the adopt branch would then never run. Use `getTenantOwnership()` as the primitive and layer `isTenantVisible()` / `isTenantAdoptable()` on top; routes call the request-bound wrappers in `src/api/store/saas/lib/tenant-ownership.ts` and must never re-type the comparison (the original bug was five drifted inline copies, one of which answered a mismatch with `{subscriptions: []}`).
* **Never Filter On A Missing jsonb Key**: `payment_context` is a nullable JSON column, so for every pre-existing row `payment_context->>'mechanism'` is NULL and `NULL != 'native'` evaluates to NULL — not true. An exclusion filter written that way returns **zero rows**, so the guard looks correct, passes a hand-built test with a fresh row, and does nothing in production. Recognize provider-owned subscriptions by their `NATIVE-` reference prefix instead (`src/modules/subscription/utils/native-subscription.ts`; `reference` is NOT NULL, unique and indexed, and Medusa's filter operator map supports `$like`). Writing `mechanism` on new rows as human-readable context is fine; using it as a predicate is not.
* **Qualifying to_regclass Defeats search_path**: `to_regclass('schema.table')` resolves the schema it *names* and ignores `search_path` entirely, so in a hand-written migration whose surrounding statements use unqualified table names the guard can answer for a different table than the join sitting beside it. Measured on Postgres 16 with `search_path = r1_ns, public` and `subscription` present in `r1_ns` only: `to_regclass('public.subscription')` is NULL while plain `FROM "subscription"` in the same session reads `r1_ns.subscription`, so the guarded branch silently degraded to the fallback ordering and soft-deleted the wrong rows. Rule: in a migration that otherwise names tables unqualified, write `to_regclass('"table"')` (a quoted bare name resolves through `search_path` exactly like the join does) and prove it on a scratch database with a non-public `search_path`, because the failure mode is a no-op, not an error — see `src/modules/renewal/migrations/Migration20260924120000.ts:35-53`.
* **Rollback Must Derive Its Field List From The Write**: a compensation that restates the columns its write touched drifts the moment either side changes. The `adopted` rollback wrote `scheduled_for`, the approval state and `metadata` but restored only the date, so a rolled-back row kept a half-applied repair. Rule: declare the writable set once and derive the restore type from it (`UpcomingCycleReconcilePatch` and the `-?` mapped `UpcomingCycleReconcileRestore`, `src/modules/renewal/utils/upcoming-cycle.ts:45-68`, snapshotted by `restoreForUpcomingCycleReconcile` `:127-139`, written once at `src/workflows/steps/ensure-next-renewal-cycle.ts:407-446`), so adding a column to the write without adding it to the rollback is a compile error. A comment claiming the two agree proves nothing — an `Exclude`-style assertion that stays green when the type widens is worse than no assertion, and `src/modules/renewal/__tests__/upcoming-cycle.spec.ts` replaces it with one that reddens.
* **A Residual Recorded Only In Gitignored Notes Is Unrecorded**: `.superpowers/**` and `.scratch/**` are invisible to the next reader, so a finding that lives only in a ledger or a review package has zero effect on the codebase. Rule: every "known, deliberately not fixed here" item a maintainer must know about lands in the repo — `docs/architecture/*.md`, `.agents/lessons.md`, or `CHANGELOG.md` — before the round is called done. Examples from this round: the out-of-band mirror-deletion gap (now in `docs/architecture/subscriptions.md`, *Known limitation*), the normalization that `down()` does not undo (now in `CHANGELOG.md`), and the empty-product-title wording quirk (below).
* **Engine Failures Are Serialized Objects, Not Errors**: `run(id, { throwOnError: false })` returns `errors[]` entries of `{ action, handlerType, error }` where `error` is `serializeError`'s literal plain object (`@medusajs/utils/dist/common/serialize-error.js` copies `{ message, name, stack }` plus every own enumerable property), so `errCtor: "Object"`, `isError: false`, and `instanceof Error` is **never** true for anything the engine reports. Two consequences: (1) tell a guard's refusal from an infrastructure fault by the step's registered name — exported as a constant or read from `step.__step__` — never by `instanceof` (`src/workflows/steps/set-subscription-auto-renew.ts:22-34`, `src/workflows/utils/store-step-failure.ts:49-66`); (2) never rethrow the deserialized value, because `code`/`table`/`detail` survive serialization and `formatException` (`@medusajs/framework/dist/http/middlewares/exception-formatter.js`) switches on `err.code`, mapping 23505→422, 23503→404, 23502→400 with the table and column names in the body. Most driver errors are already converted by the DAL (`mikro-orm-repository.js` → `db-error-mapper.js`) into MedusaErrors whose *messages* still carry those names, which is why `database_error` is deliberately absent from the preserved list at `src/workflows/utils/store-step-failure.ts:132-139`. Throw a freshly constructed `MedusaError` with fixed text and log the raw value instead. Two corollaries measured the same day: **(a) the rule covers every caller, not just the routes it was written for** — `throwOnError` defaults to `true` (`@medusajs/workflows-sdk/dist/helper/workflow-export.js:99`), and the engine then does `throw ret.errors[0].error` (`@medusajs/workflow-engine-inmemory/dist/services/workflow-orchestrator.js:130-133`), i.e. a caller that never looks at `errors` rethrows the *serialized* object, so a workflow shared between a bridge route and a customer-session route discloses internals on the second one until it classifies too. **(b) a whitelist's third element is the only one with teeth** — matching a declared refusal on step and `MedusaError` type alone still quoted `column redemption_code.redemption_cont does not exist` to a storefront, because the DAL's `db-error-mapper` turns a schema fault on a guard step's own read into an `invalid_data` carrying that step's name; the exact-text test (`refusal.copy.test(message)`) is what makes the declaration mean something. If you add a `CustomerRefusal` field, assert the classifier reads it.
* **A jsonb Write Merges On One Path Only**: `updateSubscriptions` merges one key of a jsonb column because it reaches `manager.assign(entity, update, { mergeObjectProperties: true })` (`@medusajs/utils/dist/dal/mikro-orm/mikro-orm-repository.js:224-230`) and `EntityAssigner.js:106-108` merges when **both** the stored and incoming values are plain objects (`Utils._merge` then recurses). That merge is path-dependent, not universal: the batch path `nativeUpdateMany` (`mikro-orm-repository.js:868`, reached from `upsert` `:286` and `upsertWithReplace` `:351`) overwrites the column, and a stored non-object takes the non-merging branch too. Writing `metadata: null` clears the whole column, so "no writer can clear a metadata key" is false as a documentation statement. Rules: never write an incomplete jsonb payload on the assumption the framework merges it — re-read and spread the stored object, as every subscription `metadata` writer now does (`docs/architecture/subscriptions.md`, *The `metadata` jsonb column*) — and never describe such a case as customer data loss without checking which DAL method ran.
* **A Cosmetic String Is Not A Pinned Contract**: an empty product `title` reaches the checkout refusal verbatim (`for ''`) — `readProductTitle` substitutes the product id only when the product row is missing or its title is `null`/`undefined` (`src/modules/subscription/utils/native-exclusivity.ts:95-113`), and both refusal messages interpolate that value (`src/modules/subscription/utils/checkout-gate.ts:193-205` and `src/workflows/steps/validate-subscription-cart.ts:550-555`). Nothing pins the wording or the reachability. It *is* reachable, because the framework's product validators type `title` as `z.string()` with no minimum length in both the create and the update schema (`@medusajs/medusa/dist/api/admin/products/validators.js:167` and `:207`), so `""` is not a value anything rejects. Rule: check the framework's own validators before writing "unreachable" into a doc, and label a known-but-unpinned behavior as one rather than leaving it only in a review note.
* **Whole-File Restore Is Exclusive Ownership**: in a shared working tree, `cp file.bak file` on a tracked file is a claim on the **whole file**, not an edit within it. Observed: one agent's verified comment-only fix was reverted when a sibling restored its backup mid-round, and the result still compiled, so nothing surfaced the loss. Rule: no second agent may be dispatched into a file while any mutation-probe/restore loop is live there, and an ownership map must list restores explicitly, not just edits. Corollary for evidence: `.superpowers/**`, `.scratch/**` and any `/tmp` evidence directory must be namespaced **per task**, because a shared "before" snapshot can already contain another wave's executable mutation probe — a diff against it then measures the wrong baseline and a reviewer certifies a state nobody wrote. Second form of the same mistake, measured the hard way: `medusa plugin:build` **deletes and rewrites `.medusa/server`** (`info: Removing existing ".medusa\server" folder`), and that is the directory a live `test:integration:http` run loads the plugin from — so rebuilding while an http suite is in flight does not just dirty the evidence, it fails suites that had nothing wrong with them (observed: four `FAIL`s, two of them mid-suite with real test names, from nothing but a rebuild under a running gate). A build is a whole-directory restore and owns the tree exactly like a `cp` does: never run one, or edit anything under `src/`, while a gate or a read-only reviewer holds it.
* **A Hand-Restated Container Reader Checks Nothing**: `container.resolve` is keyed by string, so re-declaring a module method locally (`listSubscriptions(filter: MyFilter): Promise<MyRow[]>`) typechecks nothing the container has to satisfy; renaming or re-signing the real method degrades from a compile error into a runtime `TypeError` inside a step, invisible to a suite that pins the filter with `toHaveBeenCalledWith`. Rule: derive the reader from the service (`Pick<SubscriptionModuleService, "listSubscriptions">`, plus a row type taken off the method's own return, `src/modules/subscription/utils/stacking.ts:87-101`) and narrow the key (`resolve(key: typeof SUBSCRIPTION_MODULE)`, `:104-114`), since a `resolve(key: string)` that answers *any* key with the reader type is the same hole as the generic `<T>(key: string) => T`. This costs no cast at the call site. Where the boundary is genuinely untyped, say which guarantee lives where: generated module methods take `filters?: any`, so a query shape is pinned **behaviourally** by `toHaveBeenCalledWith`, and only the runtime branch covers a projection that stops selecting a column (`resolveConsentFlip`'s `reference_undecidable`, `src/modules/subscription/utils/consent-flip.ts:102-111,168-170`).
* **A Step That Matches By Exact Date Tolerates A Moved Anchor**: `ensure-next-renewal-cycle` looked for a cycle whose `scheduled_for` equalled `subscription.next_renewal_at` to the millisecond and created another when it found nothing, so once a stacked purchase moved the anchor the lookup missed by construction and the row gained a second live `SCHEDULED` cycle — both chargeable, and nothing on either row said so. Rule: when a row's role is "the one standing for X", reconcile by role (match / adopt / defer / create, `src/modules/renewal/utils/upcoming-cycle.ts:220-258`) instead of by equality on a mutable field, and make the invariant a **partial unique index** (`Migration20260924120000`) so future drift is a loud error rather than a charge. Decide what an in-flight child record means before choosing: moving a cycle whose renewal order already exists re-arms billed money, which is why `defer` exists as a required branch and not an edge case.
* **A Hand-Authored Partial Index Is Invisible To The Generator**: MikroORM *can* express a unique index and its generator already emits `CREATE UNIQUE INDEX … WHERE deleted_at IS NULL` in this repo (`src/modules/redemption/migrations/Migration20260909120000.ts`), so the only thing that forces a hand-written migration here is an extra `status = 'scheduled'` predicate — and a later `medusa plugin:db:generate` has no model to compare it against, so it may propose dropping an index whose loss restores the bug. Rule: such indexes carry an in-migration comment naming the intent (`Migration20260924120000.ts:11-19`), the release notes say what `up()` destroys and that `down()` does not undo it, and an unqualified `create unique index … where …` predicate must be checked against the soft-delete convention the generator uses.
* **Module Runners Never Apply Hand-Written Migrations**: nothing in this repository passes `pathToMigrations`, so `@medusajs/test-utils` takes the `orm.schema.refreshDatabase()` branch for `src/modules/*/__tests__` runners — the schema there is derived from the entity models, and a migration's output simply does not exist in that suite. Rule: any assertion about a migration (a partial unique index, a CHECK constraint, a normalization) belongs in `integration-tests/http/`, which does run plugin migrations; a module-level test for it cannot even fail. The same `jest.config.js` `testMatch` decides where a *decision unit* may live: only `src/modules/*/__tests__/**/*.spec` and `integration-tests/http/*.spec` execute, so a rule placed under `src/api/**` or `src/workflows/__tests__/` is untestable where it is written. Also note `medusa plugin:build` typechecks `src/` and `src/modules/*/__tests__/**` but **not** `integration-tests/**`, so a type-level guard has teeth in the module tests and not in the http specs — and with no CI workflow in this repo, even that gate runs only when someone runs it.
* **One Sensitive-Key Set, Asserted Through Both Writers**: masking lists must never be restated per consumer. The error serializer and the log normalizer each held a private list and had drifted apart in **both** directions (`api_key`/`secret`/`token` on one side, `address_1`/`address_2`/`postal_code`/`phone`/`payment_reference`/`raw_error` on the other), so "wider/narrower" is the wrong frame and the merge is a union. Rule: one exported set under the owning module's `utils/` imported by every writer (`src/modules/activity-log/utils/sensitive-keys.ts:49`) — under `src/modules/**`, not beside the route or step that consumes it — and specs that assert **behavior through each writer** (build the expected key list locally in the spec and show every member is masked and nothing else is) rather than membership of the exported constant, because a contents-pin stays green when a consumer reintroduces its own private list. Widening the set is a security change: the pins going red is the expected workflow, not a reason to add fewer keys.
* **A Migration Is Only Real Where a Runner Applies It**: no runner in this repo passes `pathToMigrations`, so `@medusajs/test-utils` reaches `orm.schema.refreshDatabase()` for module suites and the migration output simply does not exist there — while the http suites *do* run the plugin's migrations through `migrateDatabase → runModulesMigrations` (`@medusajs/test-utils/dist/medusa-test-runner.js:100`). Rule: assert migration behaviour in `integration-tests/http/`, and when a migration *shapes* data rather than constraining it, drive it on a probe database built with `getMikroOrmWrapper` (`@medusajs/test-utils/dist/database.js:73,100-128`) and prove it reaches the same `mikro_orm_migrations` set the app bootstrap writes. Passing `pathToMigrations` by hand is a harness, not a runner — nothing that *runs* these suites passes it, and that distinction is the whole lesson. Naming a framework API without citing the file and line that proves it exists is a plan defect: `Migrator.runMigrationClasses()` did not exist here. What building that harness (`integration-tests/http/migrations.spec.ts`, Phase 2 of the 2026-09-25 plan) measured on top of the rule:
  * `getMikroOrmWrapper`'s multi-directory branch runs each dir through `runMigrationsFromPath` and then **returns** (`database.js:122-129`), so explicit sources own the schema and nothing entity-derived is layered on — but the wrapper's own ORM is configured with `pathToMigrations: migrationPaths[0]` (`:107`), so `wrapper.orm.getMigrator()` can never see a later directory's migration and a `down({ migrations: […] })` asking for one answers the loud `Couldn't find migration to apply with name` (`umzug/lib/umzug.js:317-326`). Bind a migrator to the directory you mean (`withMigratorFor`), the way `runMigrationsFromPath` itself does — `getMikroOrmConfig` + `MikroORM.init` + `discovery.warnWhenNoEntities`, which keeps `CustomDBMigrator` in play and so stays the same entry point `medusa migrate` uses. Second trap in the same branch: a **single**-directory wrapper whose directory has nothing pending falls through to `orm.schema.refreshDatabase()` (`:138-140`) and regenerates the schema from the entities over the database you believed you had migrated. Build a one-dir probe only over a database created moments before, never call `setupDatabase()` on an already-migrated one, and assert the applied **set** so a fall-through cannot pass quietly.
  * `dbTestUtilFactory()` exposes `create / snapshot / restore / dropTemplate / teardown / shutdown` — **no `delete`, no `execute`** — and its `create` calls `createDatabase(…, { errorIfExist: false })` (`@medusajs/test-utils/dist/medusa-test-runner-utils/postgres-template.js:158`), which swallows the duplicate-database error. A probe database leaked by an OS-killed worker is therefore **silently reused** by the next run, and its greens are read off a schema that process never migrated. Teardown is `shutdown(name)` *before* `create(name)` plus `try { orm.close() } finally { drop() }` at every exit (drop is `shutdown`, and it already runs `errorIfNonExist: false` and terminates stale connections); a `finally` that can itself throw must box the body's error and append the teardown note rather than replace it.
  * `getPendingMigrations()` yields `{ name, path? }` — there is **no `label`** in MikroORM 6.6.14 (`@mikro-orm/migrations/Migrator.js:197` → `umzug.pending()`), which is exactly what `database.js:136` maps. A plan snippet writing `m.label ?? m.name` is not wrong-by-taste, it is wrong-by-absent-field.
  * Probe-side and app-side read **different trees**. The probe points `pathToMigrations` at `src/modules/*/migrations/*.ts`, which jest resolves through the `@swc/jest` transform, so a `src`-only mutation is live with no rebuild. The app bootstrap resolves the plugin through `package.json` `exports` → `.medusa/server/src/modules/<dir>` (`load-internal.js:367`, migration path at `:419`), so an app-side probe must `corepack yarn build` after mutating **and** after restoring, or it reports a green belonging to the previous bytes. See the corrected bullet above for the directory name.
  * Which mutation you choose matters as much as the rebuild, and the dividing line is whether `up()` still **succeeds**. A mutation that makes `up()` throw — neutralize the `to_regclass('"subscription"')` guard so `entitlement_join` is emitted unconditionally, or break a module-level constant that feeds the SQL it assembles (`NEXT_EVENT_TYPES`, `src/modules/activity-log/migrations/Migration20260922120000.ts:6`) — makes the shared nine-directory `beforeAll` reject, and jest inherits one hook error into **every** case of that describe (measured: 8 failed / 8 total, all 16 stack traces pointing at the `beforeAll`), so detection is real but attribution is gone. A mutation `up()` survives — `prefer_entitlement := ''` (`src/modules/renewal/migrations/Migration20260924120000.ts:62`), or anything below a `down()` — reddens exactly the cases that read it, because the hook still migrates cleanly. Put revert cases in a describe with no hook that runs `up()` (`withSoloProbe`), and never "fix" the poisoning by reordering the shared list: that order (renewal 7th, before `subscription` creates its table) *is* the first-install path the guard case asserts, and a temporary reorder is a throwaway that has to be disclosed, not committed.
  * `integration-tests/**` is typechecked by **no gate**: `medusa plugin:build` covers `src/` and `src/modules/*/__tests__/**` only, and `@swc/jest` strips types silently — there are 90 pre-existing `error TS` across 18 files there. Anyone adding a spec under `integration-tests/` must typecheck it by hand and prove the file was in the program: `npx tsc --noEmit -p tsconfig.json --listFiles | grep -c <spec>` then `… | grep -c <spec>` for its errors, or a `0` just means nothing was checked.
